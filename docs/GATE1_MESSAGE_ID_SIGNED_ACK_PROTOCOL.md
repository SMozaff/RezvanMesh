# RezvanMesh — Message Delivery and Acknowledgement Protocol

**Status:** Current implementation  
**Last reviewed:** 2026-09-26

## 1. Current protocol state

RezvanMesh currently has **no active remote delivery acknowledgement protocol for direct messages**.

The application can currently establish local evidence that a message was accepted for processing/queueing. It must not represent that event as proof that the recipient:

- received the packet,
- decrypted it,
- stored it,
- displayed it, or
- read it.

This is intentional. The implementation fails closed rather than presenting an unverified delivery claim.

## 2. Current direct-message path

The current direct-message path is:

```
UI
 ↓
Android repository / ViewModel
 ↓
RezvanRadioService
 ↓
ActionDispatcher
 ↓
BLE/GATT transport
 ↓
MeshEngine
 ↓
routing + session + decryption
 ↓
recipient application
```

The mesh packet sequence number is a routing/protocol value. It is **not** currently a persistent application-level message identifier.

## 3. Current truthful states

The UI/data layer should distinguish local processing from remote evidence.

| State | Evidence available now |
|---|---|
| Queued/local | Android persisted the outbound message locally |
| Local transport accepted | Native/radio layer accepted the packet/action for local processing |
| Failed locally | Local session, route, or transport submission failed |
| Remote received | **Not currently generated by a protocol acknowledgement** |
| Read | **Not implemented** |

A GATT callback or successful local write must never be interpreted as remote delivery.

## 4. Why a remote ACK is not currently enabled

A trustworthy remote delivery state requires all of the following:

1. a persistent application message ID;
2. authenticated binding of that ID to sender and recipient;
3. durable recipient-side persistence;
4. an authenticated acknowledgement;
5. replay/duplicate protection;
6. sender-side validation that the acknowledgement belongs to the exact message;
7. retry behavior that preserves the same logical message identity.

Without those controls, an apparent "delivered" indicator would be misleading.

## 5. Existing security boundary

Direct-message encryption and peer authentication remain separate from delivery semantics.

The current cryptographic/session layer provides confidentiality and authentication for the supported message path. It does not itself prove that a remote Android database committed the message.

The same distinction applies to emergency and channel messages. Their successful local dispatch does not constitute a remote delivery receipt.

## 6. Current channel and emergency semantics

### Channels

Channel messages use sender-key encryption and the normal mesh transport/relay path.

There is currently no channel-wide delivery receipt protocol.

This is deliberate: acknowledgement fan-out can multiply traffic rapidly in a mesh and requires a separate protocol design.

### Emergency broadcasts

Emergency messages use the flooding/relay protocol.

There is currently no application-level "all recipients received this" guarantee.

A node receiving and relaying an emergency packet is observable through diagnostics, but that is not equivalent to a network-wide delivery guarantee.

## 7. Future delivery protocol requirements

If remote delivery receipts are introduced, the implementation must define and test:

- stable 128-bit application message IDs;
- encrypted message-ID envelopes;
- recipient-side durable deduplication;
- authenticated ACK signatures;
- sender/recipient/message binding;
- ACK replay protection;
- ACK retransmission/outbox behavior;
- legacy-peer fallback;
- UI semantics that distinguish local acceptance from remote receipt;
- privacy-preserving diagnostics.

The protocol must remain additive so that older nodes can continue exchanging legacy direct messages.

## 8. Required tests before enabling remote receipts

### Software tests

- message-ID serialization and validation
- duplicate inbound suppression
- retry preserving the same ID
- invalid ACK rejection
- wrong-recipient ACK rejection
- wrong-message ACK rejection
- replayed ACK idempotence
- ACK-before-persistence rejection
- process death around message/ACK persistence
- legacy-peer fallback

### Device tests

At minimum:

1. A sends to B.
2. B persists the message.
3. B returns the authenticated ACK.
4. A validates and displays the remote-received state.
5. Drop the ACK and retry the message.
6. Confirm the same message ID is used and B does not display a duplicate.
7. Kill either process at each stage.
8. Change the route between message and ACK.
9. Tamper with the packet and confirm no delivery state is produced.

## 9. Current acceptance boundary

Until the above protocol exists and is tested, the maximum truthful user-facing claim is:

> **Queued / accepted locally**

The application must not claim:

> Delivered  
> Received  
> Read

unless those states are backed by explicit protocol evidence.

## 10. Relationship to current project status

This document replaces the previous Gate 1 implementation proposal. It intentionally describes what the repository does **today**, not an unimplemented future protocol.

When a real acknowledgement protocol is implemented, this document should be updated in the same change as the wire-format implementation, database migration, tests, and UI state changes.
